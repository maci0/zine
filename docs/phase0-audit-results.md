### COM/DirectX vtable objects (deferred to future "COM guest vtable" feature):
These require allocating the entire vtable + object in guest memory AND creating
guest thunks for every vtable method. This is an architectural change beyond Phase 3:
- [ ] `d3d8/Direct3DCreate8()` — IDirect3D8 vtable (16+ methods)
- [ ] `dsound/DirectSoundCreate()` — IDirectSound vtable + IDirectSoundBuffer vtable
- [ ] `ole32/CoCreateInstance()` — generic COM vtable (64 dummy methods)
- [ ] `ole32/wmi.zig` — WbemLocator/WbemServices/WbemEnum vtables

**Why deferred**: Each vtable entry is a host function pointer that x86 code calls
via `call [eax+offset]`. On WASM, each entry needs a guest thunk (INT 0xFE stub).
This requires `x86_thunks.registerNativeThunk()` for each method, writing guest
thunk VAs into guest-allocated vtable memory. Not needed for CLI tests.

### Phase 4: PE64 support — PARTIALLY BLOCKED

Native x86_64 PE64 support only needs: PE32+ parser, Win64 calling convention thunks,
64-bit IAT patching. Does NOT need an x86_64 interpreter (host CPU runs code directly).

Interpret/WASM PE64 support IS blocked — needs x86_64 instruction decoder, 64-bit
CPU registers, etc.

See [X86_64_NATIVE_EXECUTION.md](X86_64_NATIVE_EXECUTION.md) Part 2 for details.

### Phase 5: x86_64 compat mode — TODO

Run 32-bit PEs natively on x86_64 Linux hosts using CPU compatibility mode (CS segment
switching between 32-bit and 64-bit mode). Independent of PE64 — runs existing 32-bit PEs
on a 64-bit host.

See [X86_64_NATIVE_EXECUTION.md](X86_64_NATIVE_EXECUTION.md) Part 1 for full design.

**What's needed:**
1. Sub-4GB memory (MAP_32BIT for guest allocations)
2. 32-bit guest stack allocation
3. 64→32 mode switch trampoline (iretq with CS=0x23)
4. 32→64 thunk trampolines in low memory (lcall $0x33 for API calls)
5. Signal handler updates (detect CS==0x23 faults)
6. FS segment TEB in low 4GB
